# Qorgan AI

## 1. Общая информация о проекте

Qorgan AI — система видеоаналитики для школ. Два работающих направления:
1. обнаружение возможных случаев буллинга и физической агрессии по школьным камерам;
2. распознавание учеников в столовой с фиксацией входа, выхода и продолжительности посещения.

Дополнительно планируется:
* обнаружение холодного оружия и других опасных предметов;
* идентификация учеников в помещениях;
* долгосрочный анализ изменений поведения учеников;
* аналитика активности преподавателя на уроке;
* кабинеты психолога и ответственных сотрудников;
* централизованная панель для нескольких школ.

Главный принцип: система не должна самостоятельно обвинять ученика или преподавателя.
Она должна выявлять подозрительные события, сохранять доказательный материал и передавать
его ответственному сотруднику для проверки.

## 2. Общая схема работы

IP-камера → получение кадров → уменьшение разрешения при необходимости → обнаружение людей
→ трекинг людей между кадрами → анализ движения и взаимодействия → дополнительный анализ позы
→ принятие решения → сохранение события → создание снимка и видеоклипа → запись в БД
→ отображение в веб-панели → отправка уведомления в Telegram.

Столовая:
камера входа → обнаружение лица → распознавание ученика → создание активной сессии;
камера выхода → обнаружение лица → распознавание ученика → поиск активной сессии
→ закрытие сессии → запись времени выхода и продолжительности.

## 5. Модуль обнаружения буллинга

### 5.1 Назначение
Выявлять признаки потенциальной физической агрессии: удар рукой; удар ногой; толчок;
резкое сближение; резкое изменение положения тела; физический контакт верхней частью тела;
падение после контакта; преследование; удерживание; борьба; повторяющееся агрессивное
взаимодействие.

НЕ считать буллингом: обычную ходьбу; двух учеников, идущих рядом; очередь; разговор;
приветствие; дружеское касание; массовое движение по коридору; детей, которые долго находятся
рядом без агрессивных действий.

### 5.2 Камеры
Основные камеры коридора: `hall_left_main`, `hall_right_main`.
Обработка идет примерно при FPS около 8 кадров в секунду.
При увеличении количества камер измерять реальный FPS каждого потока, а не FPS источника.

### 5.3 Детекция людей
Модель YOLOv8n, класс `person`, bounding box → трекер (сохранение ID между кадрами).

### 5.4 Трекинг
Нужен для: траектории; скорости; направления; сближения; времени рядом; резких смещений;
изменения положения относительно другого человека.
Track ID НЕ является постоянным идентификатором ученика. В модуле буллинга трекер отвечает
только за движение, а не за распознавание личности.

### 5.5 Анализ движения
Признаки пары: расстояние; изменение расстояния; скорость сближения; скорость каждого;
относительная скорость; направление; резкое смещение; продолжительность рядом; возможный
контакт; изменение центра bbox; изменение размеров bbox.

Из текущей конфигурации известны параметры:
* порог скорости движения: около `13.75`;
* порог сближения: около `3.75`;
* минимальная относительная скорость: около `7.50`;
* минимальная вероятность первичного trigger: `0.3`;
* длительность сохраняемого клипа: около `3.0` секунды;
* cooldown между похожими событиями: около `10.0` секунд.

Эти значения не универсальны — подбирались под текущие камеры, FPS, расстояние, ракурс.
При установке в другой школе нужна отдельная калибровка.

### 5.6 Pose и skeleton
Модель YOLOv8n-pose. Ключевые точки: голова, плечи, локти, кисти, таз, колени, стопы.
Текущие параметры:
* confidence около `0.25`;
* минимальное количество анализируемых кадров ранее было `4`, позже увеличено примерно до `8`;
* максимальное окно анализа около `16` кадров;
* режим `run_on_crop=True`.

`run_on_crop=True` — pose-модель запускается не на всем кадре, а на области взаимодействия.

Skeleton ищет: `close_upper_body_contact`; `kick_like_leg_motion`; `sudden_body_displacement`;
резкое движение руки; резкое движение ноги; наклон или падение тела; изменение взаимного
положения тел.

### 5.7 Skeleton gate (ВАЖНО)
Настройка `skeleton_required_for_high_alert=True`.
Событие высокого уровня не должно отправляться как реальная тревога только на основании
скорости, движения или сближения.

Ранее проблема: система реагировала в основном на скорость сближения. Skeleton-признаки
отображались в тексте, но не всегда реально влияли на решение.

После изменений skeleton gate должен применяться ПОСЛЕ расчета итоговой уверенности и ДО
отправки тревоги. Если skeleton-подтверждение отсутствует: `_is_real_alert = False`.
Даже если основной hall-анализ дал положительное подтверждение.

ЗАДАЧА: проверить, что логика работает во ВСЕХ ветках кода, а не только в одной части
decision engine.

### 5.8 Финальный decision engine
Учитываются: движение; скорость; сближение; физический контакт; skeleton-признаки;
продолжительность; резкое смещение участника; возможное падение; поведение жертвы;
поведение агрессора; зона камеры; повторные действия.

Переменные в коде:
* `_final_confirmation_reasons` — причины финального подтверждения;
* `_final_pass_by_block` — прошло ли событие через один из сильных блоков подтверждения;
* `_weak_evidence_social_contact_block` — блокирует тревогу при слабых признаках соц. контакта;
* `_is_real_alert`;
* `_telegram_skip_reason` — должен объяснять, почему событие не отправлено в Telegram.

### 5.9 Блок слабых доказательств
Слабые причины: обычный близкий проход; кратковременный контакт; совместная ходьба; движение
в одном направлении; слабое изменение skeleton; контакт без реакции второго участника;
suppressed walking-варианты; взаимодействие без резкого displacement; отсутствие признаков жертвы.

Если только такие причины → `_weak_evidence_social_contact_block = True`, событие не
отправляется как буллинг.
ЗАДАЧА: проверить весь список `_weak_skeleton_reasons` — все варианты обычной ходьбы и
подавленного walking-события.

### 5.10 Признаки предполагаемой жертвы
Искать не только действие одного человека, но и реакцию второго: резкое смещение после
контакта; потеря равновесия; отступление назад; падение; резкий поворот корпуса; закрытие
головы/тела руками; попытка уйти; повторное приближение другого участника; асимметрия движения.

Если нет реакции предполагаемой жертвы — событие должно получать меньший вес.

### 5.11 Защита от ложных срабатываний
Фильтры: normal flow zones; mirror zones; обычная ходьба; параллельное движение; движение
в одном направлении; слабый skeleton; отсутствие контакта; отсутствие реакции второго;
длительное обычное соседство; очередь; массовое движение; cooldown; повтор события;
недостаточное число кадров; отсутствие pose-подтверждения; слабый motion; контакт без
резкого displacement.

* **Mirror zones** — участки, где зеркало создает ложные детекции.
* **Normal flow zones** — участки, где люди обычно идут в одном направлении; сближение
  оценивается мягче.
* **Staircase zones** — предусмотрены, но сейчас их количество РАВНО НУЛЮ. Если появятся
  камеры на лестнице — нужна отдельная логика (вертикальное движение, перекрытия, изменение
  размеров bbox могут восприниматься как падение/резкое сближение).

## 8. Модуль столовой

### 8.1 Назначение
Фиксирует: кто вошел; во сколько; кто вышел; во сколько; сколько времени был в столовой.
Две камеры: вход и выход.
По текущей конфигурации упоминались камеры/адреса: вход — `1.12`; выход — `1.6`.

### 8.2 Главное правило входа и выхода
Камера входа может создавать новую активную сессию.
Камера выхода НЕ должна создавать новую сессию.
Камера выхода работает только если для распознанного ученика уже есть активная сессия.

вход распознан → запись с временем входа → статус active → выход распознан → поиск active
session → время выхода → продолжительность → сессия закрыта.

Если выход распознал ученика, но активной сессии нет — новая запись создаваться НЕ должна.

### 8.3 Распознавание лица
Фото из `student_photos` → face embeddings.
При обнаружении лица: вырезается; проверяется качество; создается embedding; сравнение с базой;
лучший кандидат; проверка порогов; решение.
Желательно несколько фото одного ученика: анфас; поворот влево; поворот вправо; нейтральное
выражение; при разном освещении.

### 8.4 Exit Buffer
На камере выхода — буфер распознавания. Причина: лицо видно только на 1–2 кадрах, а полный
цикл обработки камеры может занимать больше времени.

Текущие параметры:
* окно около `2.5` секунды;
* от `3` до `7` попыток распознавания;
* soft thresholds около `0.34 / 0.12`;
* hard thresholds около `0.45 / 0.22`;
* cooldown после неудачи около `2.0` секунд;
* буфер ведется отдельно для каждого track ID.

Смысл: hard threshold позволяет принять сильное совпадение сразу; soft threshold может
требовать несколько подтверждений; второй параметр может использоваться как разница между
лучшим и вторым кандидатом либо как дополнительный критерий качества.
ЗАДАЧА: проверить точное назначение обоих значений в текущем коде и задокументировать.

### 8.5 Оптимизация камеры выхода
Ранее камера выхода работала медленно: один цикл сканирования занимал примерно **1.4–3 секунды**.
Из-за этого система анализировала старые кадры и пропускала момент, когда лицо хорошо видно.

Введен параметр `exit_watch_max_frames_per_scan = 2`. Приоритет отдан самым свежим кадрам.

Принцип: не обрабатывать очередь устаревших кадров; брать последние доступные кадры; не
позволять face recognition блокировать прием видеопотока; ограничивать количество тяжелых
распознаваний за цикл.

### 8.6 ROI камеры выхода
В режиме отладки: оранжевая зона — `exit_face_search_roi`; зеленая рамка — bbox человека от YOLO.
Текущее рабочее разрешение упоминалось как `960×540`.

Face recognition на выходе запускать только в ROI. ROI должна: находиться перед камерой;
не быть слишком большой; не захватывать дальнюю часть помещения; учитывать рост детей;
учитывать направление движения.

### 8.7 Известная проблема закрытия сессии
Камера выхода правильно распознавала ученика, но активная сессия не закрывалась.

Проверить цепочку:
1. правильно ли определен student ID;
2. существует ли active session;
3. одинаковый ли ID ученика на входе и выходе;
4. не закрыта ли сессия ранее;
5. нет ли ошибки времени или часового пояса;
6. выполняется ли commit в БД;
7. не перезаписывается ли статус;
8. не работает ли фильтр минимальной продолжительности;
9. не блокирует ли повторное закрытие cooldown;
10. не происходит ли поиск сессии по неверной школе или камере.

Логировать: лицо распознано; student ID найден; активная сессия найдена или нет; session ID;
запрос на закрытие выполнен; количество измененных строк; итоговый статус.

## 12. Новые модули, которые нужно реализовать

### 12.1 Обнаружение холодного оружия
Целевые классы (первый этап): нож; топор; дубинка; металлический предмет, похожий на оружие;
огнестрельное оружие при наличии подходящей модели.

НЕ отправлять тревогу по одному кадру. Схема: объект обнаружен → отслеживание несколько кадров
→ проверка confidence → проверка нахождения рядом с человеком → повторное подтверждение
→ snapshot и clip → критическое уведомление.

Ложные объекты: телефон; ручка; линейка; ножницы; кухонные предметы; игрушки; элементы одежды.
Для столовой и кухни правила должны отличаться от коридора (нож на кухне — рабочий предмет).

### 12.2 Распознавание учеников за пределами столовой
Единый сервис идентификации личности для: столовой; входа в школу; коридоров; классов;
посещаемости; модуля поведения.

Нельзя запускать тяжелое распознавание каждого человека на каждом кадре. Нужна архитектура:
person tracking; выбор лучшего кадра лица; распознавание один раз; привязка student ID к
track ID; обновление только при потере трека; кэширование результата; хранение confidence.

### 12.3 Анализ поведения учеников
НЕ определение эмоции по одному кадру. Задача — отслеживать изменения поведения в течение
длительного периода: частота присутствия; активность движения; участие в группах; частота
нахождения в одиночестве; изменения обычного поведения; длительное снижение активности; резкое
увеличение конфликтных взаимодействий; частые случаи рядом с тревожными событиями; регулярные
опоздания; длительное отсутствие; изменение вовлеченности на уроке.

Результат — не диагноз, а сигнал: «У ученика наблюдается устойчивое изменение поведения.
Рекомендуется проверка школьным психологом».
Сравнивать ученика прежде всего с ЕГО СОБСТВЕННОЙ предыдущей нормой, а не с другими детьми.

### 12.4 Анализ класса
Отдельная камера с обзором учеников. НЕ определять точную эмоцию каждого ребенка с дальнего
расстояния.

Реалистичные показатели: присутствует ли ученик; на месте ли; поднял ли руку; смотрит ли в
направлении доски; длительно ли лежит на парте; часто ли отворачивается; активно ли
перемещается; участвует ли в групповой работе; изменилось ли поведение относительно прошлых недель.
Все показатели агрегируются. Нельзя делать вывод «ученик грустный» только по выражению лица.

### 12.5 Анализ преподавателя
Объективные действия: находится ли в классе; стоит ли у доски; перемещается ли по классу;
взаимодействует ли с учениками; использует ли доску; длительно ли сидит без движения; сколько
времени вне видимой зоны; как распределена активность по уроку.

Система НЕ должна утверждать, что преподаватель «плохо преподает». Правильный результат:
процент времени у доски; процент времени в движении; процент времени взаимодействия;
длительные периоды без активности; вовлеченность класса как отдельный показатель.
Оценка качества остается за администрацией школы.

## 13. Кабинет психолога
Психолог должен видеть: учеников с устойчивыми изменениями поведения; историю сигналов;
подтвержденные случаи буллинга; повторяющиеся конфликты; частоту нахождения в одиночестве;
посещаемость; комментарии классного руководителя; статус работы с учеником.

Ограничить доступ: психолог не должен видеть все административные настройки, а обычный
оператор не должен видеть конфиденциальные записи психолога.

## 14. Роли пользователей
* **Суперадминистратор**: управление школами; серверами; всеми настройками; пользователями.
* **Администратор школы**: камеры своей школы; события; ученики; столовая; отчеты.
* **Оператор безопасности**: просмотр тревог; подтверждение/отклонение событий; просмотр клипов.
* **Психолог**: сигналы по ученикам; подтвержденные случаи; история наблюдений; свои комментарии.
* **Сотрудник столовой**: активные посещения; статистика столовой; БЕЗ доступа к буллингу и
  психологическим данным.

## 15. Логирование
Каждый модуль пишет структурированные логи.
* Буллинг: camera ID; track IDs; motion score; skeleton score; причины; блокирующие причины;
  итоговое решение; причина отправки/пропуска Telegram.
* Столовая: camera ID; track ID; лицо найдено или нет; качество лица; лучший кандидат;
  confidence; второй кандидат; active session; результат создания/закрытия сессии.
* Камеры: подключение; отключение; количество переподключений; фактический FPS; задержка;
  размер очереди кадров.

## 16. Производительность
При увеличении числа камер разделить процессы: прием видеопотока; детекция; трекинг; pose;
face recognition; сохранение видео; API; Telegram.

Нельзя выполнять все тяжелые операции последовательно в одном цикле.
Использовать: очереди с ограниченным размером; приоритет свежих кадров; пропуск устаревших
кадров; отдельные worker-процессы; batching; GPU inference; контроль VRAM; watchdog.

Для каждого потока отображать: input FPS; processed FPS; dropped frames; inference time;
задержку от реального времени; загрузку GPU; ошибки.
